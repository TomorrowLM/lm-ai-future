# DSH 拓扑编排：节点调度设计记录

> 本文记录已确定的需求、实现方案及当前实现边界。当前代码已实现“活动主会话启动 DSH 子代理 → 核验子代理结果 → 人工确认 → 更新用户指定 JSON”的固定流程切片；完整画布 DAG、Goal 完成协议和恢复尚未完成。DSH 接口说明以 v0.2.2-rc.3 为依据，接入其他版本时需重新核对。

## 1. 设计目标与基本约定

### 1.1 运行底座与职责

以 DSH Harness 为运行底座，用户使用可视化画布搭建任务流程，并通过主会话与主 Agent 对话。首节点固定为主会话，不能修改节点类型；后续节点可以使用会话执行、启动子代理、等待人工确认或由自定义插件执行。

DSH 提供 Agent、Session、子代理、工具和运行时事件。中台维护流程定义、节点状态、前置依赖、节点生命周期和调度；DSH 不直接识别画布中的节点及连接。

采用**中控调度器 + 运行状态文件**：中控是中台内负责执行流程的调度组件，不是要求用户对话的额外 Agent。它接收 DSH、用户或节点插件的结果，判断状态和依赖并启动后续节点；JSON 负责持久化运行状态和结果引用，供展示及恢复。两个部分各司其职，不依赖节点之间直接互相通知。

### 1.2 节点类型与执行会话

节点类型决定执行方式；执行会话决定关联哪个 Agent 的上下文，两者分别配置。用户仍通过根主会话交互，子代理会话是可选的执行上下文，并不因此成为根主会话。

后续节点默认选择发起添加的父节点关联会话，也可显式选择根主会话或其他可用会话。子代理节点由所选会话创建子代理；自定义节点是否使用会话及如何执行，由插件契约定义。多个父节点时的默认会话及可选范围待设计。

首节点是唯一的根主会话入口；后续的“会话步骤”是复用所选会话执行任务的节点，不创建新的根主会话。当前 HTML 尚未提供可选的后续会话步骤类型，示例中的该类型属于目标设计。

### 1.3 流程定义、运行状态与结果

流程定义描述节点、前置依赖、执行会话、完成条件和 Hook；流程运行是按某一份定义执行的一次实例。节点说明描述该节点的最终目标与预期结果；完成条件说明如何判断目标达成。

中台将运行状态记录到用户自定义位置的 JSON。节点和 Hook 的业务结果是否输出文件、输出路径和格式独立配置；未输出文件时仍需保留足以关联和传递结果的信息。

## 2. 节点关系与前置依赖

### 2.1 执行会话与节点依赖

执行依赖决定节点何时可以运行；执行会话决定节点使用哪个上下文。改变执行会话不自动改变前置依赖。

例如 `A（根主会话）→ B（子代理）→ C（自定义节点）`，C 可以默认选择 B 的会话，也可显式选择 A。结果由中台按配置传递，不假定不同会话自动共享上下文。若 B 已结束，其会话能否继续或恢复需按实际 DSH 后端验证；不可用时应等待或失败并提示，不静默切换会话。

适配器应声明会话是否支持继续对话、恢复和创建子代理。保存流程时检查可从配置推断的能力；节点启动前再次核对该次运行的实际会话和能力。不可继续或能力未知时，中控不启动并展示原因，等待用户调整或按失败策略处理；不允许把未知视为支持。会话恢复权限、后端类型与实际行为须通过 DSH 接入验证。

### 2.2 前置依赖的配置规则

1. 首节点是流程入口，不设置前置依赖。从某个节点新增子节点时，默认勾选发起添加的节点；用户可取消或更改。
2. 列表排除当前节点、会形成直接或间接循环的节点，以及已通过其他已选前置节点间接依赖的节点。无相互依赖的兄弟节点仍可按需选择。
3. 例如 `A → B → C` 中，C 已通过 B 等待 A，无需再选择 A。用户更改选择时，候选列表实时更新；取消 B 后，A 可重新选择。
4. 已勾选的重复依赖保留并提示“已间接依赖，可取消”，不自动删除；保存时仍校验循环依赖。若后续移除 `A → B`，不会自动给 C 添加 A，用户可按需重新配置。

间接依赖的去重规则只适用于当前“全部成功”条件；支持“任一成功”等其他汇合条件时需重新评估。

### 2.3 顺序、并行与汇合

有前置依赖的节点默认等待全部直接前置节点成功后启动。没有相互依赖的节点可以并行调度；多个节点使用同一会话时，实际并发能力、输入顺序及结果归属需要验证。任一成功触发、失败继续及其他汇合策略待设计。

### 2.4 画布与连线展示

- 节点按依赖层级自动排布；实线箭头从前置节点指向后置节点，卡片底部单独标注执行会话。
- 连线目标状态为灰色表示未满足、绿色表示已满足、红色表示阻塞；当前 Demo 仅提供对应样式，没有真实运行状态。
- 相邻层使用曲线；跨层连线在经过的节点范围上方或下方择近绕行，并使用圆角转折。当前为简化路由，复杂拓扑中的多线交叉仍需进一步处理。

## 3. 节点调度与状态流转

以下先说明目标调度方案；第 7 章单独列出已经落地的固定流程切片和未实现部分。

### 3.1 节点如何进入下一步

节点不自行决定下一步；调度器依据流程定义和运行状态推进：

```text
前置条件满足 → 领取节点 → 节点开始前 Hook → 启动执行
→ 接收结果 → 检查完成条件 → node/before-complete 必需 Hook
→ 记录节点成功 → node/completed 成功通知 → 检查后续节点的前置条件
```

例如 `A（主会话）→ B（子代理）→ C（子代理）`：中控启动 B，接收 B 的结果并检查完成条件，统一更新运行状态；随后由中控检查 C 的依赖并启动 C。B 不需要知道 C，A 不需要监听 B 后再转发启动通知。如果 C 选择 A 的会话，中控基于 A 的会话创建 C，并按配置传递 B 的结果。

节点失败、取消、阻塞或等待用户确认时，不按成功推进。需要等待的开始前或结束 Hook 未通过时，分别不启动节点或不按成功推进；具体失败策略待设计。生命周期触发的细节见第 4 章。

### 3.2 节点完成信号与完成条件

**统一执行契约（待实现）**：调度器向节点执行器传入流程运行、节点、执行次数、目标、输入、执行会话及取消信号；执行器校验能力后启动工作，并返回可关联本次执行的标识与状态 / 结果获取方式。执行器应能报告运行中、等待用户、正常结束、失败或取消；是否支持取消、重连和恢复由适配器明确声明。中控根据身份匹配和完成条件作最终判断，执行器或模型报告不直接启动下游。

| 执行类型 | 候选完成信号及判断 |
| --- | --- |
| 会话步骤 | 在适用时使用关联 Goal 的完成状态，或使用其他完成协议；一次回复可能是追问，不能单凭回复判断成功。 |
| 子代理 | 获取对应运行结果或监听结束通知，检查结束原因，再判断节点完成条件。 |
| 人工确认 | 等待用户决定；结果按配置决定是否继续。 |
| 自定义节点 | 由节点插件报告结果，再按节点配置或插件契约检查。 |

启动时，中台建议关联流程运行 ID、节点 ID、执行次数、执行会话 ID，以及子代理或 Goal 标识。收到信号时先匹配当前执行，过滤旧执行结果和重复通知；通知不一定携带完整结果，应从对应执行器的结果路径读取。

完成信号不保证目标达成：子代理可能因错误结束，Goal 的 `complete` 也可能只是调用方声明完成。完成条件可由用户确认、模型判断或插件检查；自然语言描述不保证严格执行，配置方式仍待设计。只有明确要求产物的节点才将该产物作为完成检查的一部分。

会话步骤尤其需要可靠地将输入、执行结果和节点执行次数关联。Goal 是候选完成信号，不是通用保证；不可用时必须使用经验证的其他报告 / 关联协议，否则保持等待或提示不支持。普通回复、`idle` 和 `whenIdle()` 不能单独作为特定节点成功的证明；具体接口和并发隔离需通过接入验证。

### 3.3 如何判断多个前置依赖已完成

调度器为每次流程运行维护节点状态，并从流程定义读取每个节点的直接前置依赖。D 同时依赖 B、C 时：

| B 状态 | C 状态 | D 的判断 |
| --- | --- | --- |
| 成功 | 运行中或等待确认 | 等待。 |
| 成功 | 成功 | 前置条件满足，可以进入待启动流程。 |
| 成功 | 失败、取消或阻塞 | 默认不启动，等待相应处理策略。 |

每次前置节点状态变化后，中台检查受影响的后续节点，在**同一次流程运行**中确认所有直接前置节点是否成功，再按节点配置传递上游结果。

### 3.4 失败、等待、重试与重复启动

用户补充信息、人工确认、执行失败和取消不等于成功；失败分支、重试次数、人工处理及 Hook 失败策略仍待设计。

建议的状态流转如下，状态名称和持久化格式待实现时确认：

```text
等待依赖 → 已领取 → 开始前处理 → 运行中 → 完成检查 → 成功前处理 → 成功
                                  ↘ 等待用户 / 阻塞 / 失败 / 取消
```

成功、失败、取消是本次执行的终态；等待用户或阻塞可在条件解除后按明确策略继续。重试应建立新的执行次数，旧执行结果不能覆盖新执行；是否允许自动重试和如何处理已产生的副作用待设计。只有成功状态满足默认的前置依赖；等待、失败、取消和阻塞均不按成功推进。

为防止 B、C 几乎同时完成导致 D 重复启动，建议同一流程运行内串行处理状态变化，或使用等效的原子状态转换：只有一个调度操作能将 D 从“等待”转为“已领取 / 待启动”。重复通知和旧执行次数的结果不得再次推进；具体实现和故障场景需要验证。

### 3.5 运行状态保存与恢复

用户指定的运行状态 JSON 建议记录流程定义版本或快照、节点状态和执行次数、会话与执行标识、Hook 进度及结果引用。DSH Session 另行维护会话事件，两者通过标识关联。

同一次流程运行的节点状态和可选结果地址集中记录在该运行状态文件，由中控统一维护；节点或插件报告结果，不直接并发修改共享状态文件。结果地址可为空，实际结果如何保留和传递由节点执行器及输出配置决定。中控处理运行时通知并判断依赖，不要求通过监听文件变化触发调度；重启时读取已保存状态并核对实际执行情况。

建议统一使用带类型的**结果引用**，以流程运行 ID、节点 ID 和执行次数关联；以下是设计候选，非现成的 DSH 输出格式：

| 结果形式 | 传递与恢复边界 |
| --- | --- |
| 状态 JSON 中的内联摘要 / 结构化结果 | 未配置独立输出文件时可由中控保存并传递；大小、内容与保留策略待设计。 |
| 用户配置的结果文件 | 状态文件记录位置和关联信息；读取前检查可用性。文件输出为可选功能。 |
| DSH Session 中的可恢复结果引用 | 中控记录会话和可精确定位的结果标识；只有经验证能读取和恢复时才可作为可靠结果来源。 |
| 仅内存结果 | 仅供当前进程传递；重启后不能假设仍可用。 |

中控在启动下游前解析所需上游结果，缺失或不可读时保持等待 / 阻塞并提示，不传递空结果冒充成功。需要持久化的结果及必需文件输出应确认可读取后再提交节点成功；结果写入与 JSON 更新并非同一事务，部分失败时不能认为已经完整提交，具体补偿、重试和清理策略待验证。

重启后应核对中台记录与 DSH 的实际会话、子代理和 Goal 状态，处理“已领取但尚未确认启动”等中间状态。锁、写盘、恢复和副作用去重协议待实现验证；不能仅凭一个 JSON 文件假定跨进程原子性或恰好执行一次。

## 4. 节点生命周期与 Hook

### 4.1 节点生命周期由什么触发

节点生命周期是**中台定义的扩展点**，由调度器在节点状态转换时主动触发。用户配置的 Hook 是在这些扩展点执行的动作；它们不是 DSH 自动提供的同名拓扑节点事件。

中台生命周期与 Agent 原生事件可通过统一插件接口暴露；中台自行产生节点事件，Agent 适配器接收和转换原生事件，并保留可等待、阻止和修改等能力差异。节点类型、完成判断、Hook 动作和输入输出也可扩展；中控仍统一负责状态、依赖和调度。事件映射与插件范围见[拓扑编排需求与实现方案的插件扩展与 Agent 适配](./拓扑编排需求与实现方案.md#44-插件扩展与-agent-适配)。当前只接入 DSH，其他 Agent 的能力需另行验证。

### 4.2 节点开始前与节点结束的触发流程

```text
前置条件满足 → 中台领取节点
→ 触发“节点开始前” → 等待必需 Hook → 启动执行器
→ 收集结果 → 检查完成条件 → node/before-complete
→ 等待必需 Hook → 记录成功 → node/completed 通知 → 检查后续节点
```

`node/before-complete` 是成功提交前的检查扩展点；`node/completed` 是成功状态已记录后的通知，通知失败不应倒退为“尚未成功”。`node/failed`、`node/cancelled` 表示各自结果。它们是拟定的中台事件名；无论成功失败都执行的清理事件、通知失败后的记录和重试策略仍待定义。

例如“节点开始前加载指定技能”，由中台在启动节点执行器前触发并执行对应动作。Hook 可配置动作描述及可选结果输出；具体执行器、注入时机和能力仍需验证。

### 4.3 中台生命周期与 DSH 事件的关系

DSH 事件由 DSH 在运行时行为发生时触发；中台根据会话、执行实例和事件内容匹配节点，再决定是否更新状态或执行动作：

- `subagent/end` 或子代理结果表明一次子代理执行结束，仍需区分结果和结束原因。
- `goal/changed` 通知 Goal 状态变更；`goal/change` 是 Session 记录。Goal 完成可作为候选信号，不能直接等同于中台调度下一节点。
- `step/end` 是一次模型步骤结束；一个节点可以包含多个步骤或对话轮次。
- `tools/pre-execute`、`tools/post-execute` 可用于工具调用前后处理；文件意图事件的覆盖范围取决于对应工具路径。

DSH 事件的等待、决策和修改能力各不相同，应按各自契约处理。`emit` 通知不能当成会等待中台动作的门禁；真正需要等待的节点前后置 Hook 应由调度器自身等待执行结果。

### 4.4 Hook 的等待与失败处理

开始前 Hook 未通过时不启动节点；结束 Hook 未通过时不按成功推进。失败、取消和阻塞时是否触发同一个结束事件、Hook 是否重试、超时和失败后的策略，作为生命周期契约待明确，不能视为已实现。

## 5. DSH 能力如何参与调度

### 5.1 子代理运行结果与完成通知

中台启动子代理时记录对应的执行身份，获取该次运行结果，或监听 `subagent/end` 作为结束通知。中台须匹配流程运行、节点及执行次数，区分成功、失败和取消，再结合节点完成条件判断是否推进；不能把结束通知当作任务已达成。[DSH 子代理文档](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.3/docs/subsystems/subagent.md)

### 5.2 Goal 与会话节点完成信号

在条件允许时，可使用 DSH Goal 表示会话节点目标，以对应 Goal 进入 `complete` 作为候选完成信号。中台仍需匹配会话和 Goal ID、检查节点完成条件、等待执行及必需 Hook 收尾，再决定是否推进。

以下接口以 DSH **v0.2.2-rc.3** 为依据：[Goal 服务](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.3/docs/subsystems/goal.md)、[Goal 包说明](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.3/packages/goal/goal/README.md)。

- `ctx.goals.create(agent, { objective })`：为指定活跃 Agent 创建目标并返回 Goal 视图。
- `ctx.goals.get(agent)`：读取当前 Goal；不存在时返回 `undefined`。视图中的 `id` 和 `revision` 用于精确关联和更新。
- `ctx.goals.complete(agent, ref)`：将当前目标标记完成；`ref` 包含 Goal 的 `id` 和 `revision`，过期版本会被拒绝。
- `goal/changed`：Goal 状态变更写入会话日志后发出的通知；中台需匹配 Agent、Goal ID 和状态，事件本身不调度后续节点。

Goal 服务管理状态，不负责自行启动任务；中台需投递任务，或另行接入并验证续跑组件。模型工具与服务是独立组件，须确认加载和权限。一个 Session 至多有一个当前 Goal；未完成的 Goal 不能直接被另一个替换，因此已有流程总 Goal 时不能假设节点还能同时拥有独立 Goal。

`complete` 不提供独立验收；`paused`、`blocked` 和额度耗尽不视为成功。Goal 状态保存在 Session 日志，自动续跑激活状态属于进程内状态；恢复后需按 DSH 的授权和驱动规则核对，不假设自动续跑。`agent/turn-stopping` 只是回合即将结束，`idle` 只表示当前没有活动；`followup()` 不提供单条消息完成句柄，`whenIdle()` 不能直接当作指定节点的完成通知。

### 5.3 Todo 与节点内部进度

Todo 用于展示 Agent 在节点内部的计划和进度，例如“整理输入、设计架构、输出方案”，不承担跨节点调度状态。DSH 的 `todo_write` 每次更新整份列表，Todo 项没有稳定 ID，列表属于各自 Agent Session；相关数据通过 `todo/write` Session 记录和 `todos` 投影提供，不应假定为同名 Cordis Hook。[DSH Todo 包说明](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.3/packages/todo/tool-todo/README.md)

### 5.4 会话选择与上下文传递

节点按配置选择父节点会话、根主会话或其他可用会话；流程定义保存选择规则或节点引用，运行时再解析实际 Session ID。中台检查会话是否存在、允许继续且具备所需能力，并显式传递上游结果。

DSH 自带模型工具限制子代理自行创建 Goal；中台能否为子代理创建、驱动 Goal 并协调收尾仍需验证。[DSH Goal 工具](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.3/packages/goal/tool-goal/README.md)

## 6. 完整流程示例

以下示例说明目标设计，不表示当前 HTML 已执行调度或接入 DSH。

### 6.1 子代理结果交给主会话

```text
首节点：主会话接收任务
→ A：需求分析（子代理）
→ B：方案设计（显式选择根主会话）
→ C：开发实现（子代理）
```

A 结束后，中台检查其结果和完成条件。通过后，将 A 的结果和 B 的任务交给原主会话；Goal 可用时，为 B 创建并关联 Goal。主会话可用 Todo 管理 B 的内部进度；Goal 报告完成后，中台检查目标、必需 Hook 和用户确认，再将方案交给 C。主会话已有未完成总 Goal 时，需要先解决冲突或使用其他完成方式。

B 的配置示例：

```text
节点类型：会话步骤
执行会话：根主会话（显式选择；默认来源为父节点 A）
节点说明：根据需求分析结果，完成方案设计并说明关键实现步骤。
完成条件：方案覆盖已确认的需求；如配置人工确认，还需等待用户确认。
成功前 Hook（node/before-complete）：整理方案摘要，作为开发实现节点的输入。
```

### 6.2 并行节点与多个前置依赖

```text
A：接收任务
├── B：需求分析 ──┐
└── C：技术调研 ──┴→ D：方案汇总
```

B、C 没有相互依赖时，中台可在资源和会话能力允许时并行调度。D 同时依赖 B、C，默认等待两者均成功；中台接收各自结果并更新运行状态后，检查 D 的全部直接前置依赖。只有检查通过并领取成功，才启动 D。若 C 失败或等待确认，D 默认继续等待处理。

## 7. 当前实现边界与待验证事项

### 7.1 HTML Demo 已展示的能力

`index.html` 展示画布与节点配置：首节点固定为主会话，可选择执行会话和前置依赖；节点按依赖关系排布，实线箭头表示依赖，卡片标注会话。依赖状态颜色仅作样式演示。节点配置保存在浏览器中；节点或 Hook 结果输出也是配置演示。此 HTML 尚未与 React 运行面板共享流程定义。

### 7.2 已实现：主会话 → 子代理 → 人工确认

DSH 侧栏的 React 面板提供一个固定三节点运行切片：

1. 用户填写当前活动主会话 ID、子代理目标和运行状态 JSON 绝对路径后，调用 Host 创建本次运行。
2. 中控检查主会话 Agent 是否仍活动、`spawn` 提供方是否已注册，并以独占创建方式新建状态 JSON；已存在的目标文件不覆盖。
3. 中控调用 `ctx.subagents.startActivation()`，指定 `delivery: 'caller'`、父 Agent、任务文本及流程命名，保存返回的 child Session ID，然后等待该 activation 自带的结果 Promise。
4. 仅当 `stopReason` 为 `completed` 且结果包含非空文本时，子代理节点记为成功，人工确认节点进入等待状态。其他终止原因、启动错误或空文本结果记为失败；子代理结束通知不直接推进下游。
5. 用户确认后，人工节点记为成功、流程完成；用户拒绝后，流程记为 rejected。每次状态转变写入用户指定 JSON，更新时先写同目录临时文件再替换。

**与完整设计的差异：** 面板点击即代表主会话节点触发子代理，不会检测主会话 Goal 是否完成；主会话 ID 需手动填写。当前只支持单个固定链，不解析画布 DAG、多个前置依赖、并行、节点 Hook 或自定义节点插件。运行索引只在进程内保存，重启后不能从 JSON 恢复；不保证 exactly-once。结果文本保存在状态 JSON，尚无独立结果输出配置或输出文件地址字段。

### 7.3 尚未实现或需要验证的能力

1. **主会话接入**：实现当前活动会话自动识别、Goal 监听和完成条件关联；验证输入目标是否来自会话中的真实任务，而非面板单独提交。
2. **Goal**：验证主会话的 Goal 创建、模型工具可见性、完成通知、多轮交互与精确关联；验证子代理 Goal 的权限、续跑和收尾。是否作为默认完成方式尚未确定。
3. **调度与状态**：从画布流程定义实现依赖汇合、并行、并发去重、失败处理、重启核对和副作用恢复；验证同一会话的并发及会话继续能力。当前 JSON 是已运行流程的状态记录，不是跨进程恢复协议。
4. **生命周期和 Hook**：实现触发、动作执行与等待，明确失败、取消、超时和重试语义。
5. **画布**：复杂拓扑的连线交叉、更多汇合条件及拖拽连线尚待完善。
6. **原型差异**：后续会话步骤类型尚未提供可选入口；运行结果引用、能力检查和状态机均未接入。

当前 React 面板可以运行上述固定链并写入运行状态 JSON；`index.html` 本身仍不会真正调度节点或执行 Hook。
