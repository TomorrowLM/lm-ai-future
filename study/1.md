# LangServe

## 1. 概述

LangServe 用于将 LangChain 的 Runnable 或 Chain 部署为 REST API，使其他程序可以通过 HTTP 调用模型、提示词和链。

LangServe 基于 FastAPI 提供服务，并使用 Pydantic 进行请求校验、数据解析和 Schema 生成。

## 2. 原理和机制

### 2.1 LangServe、LangChain 与 FastAPI 的关系

- **LangChain**：负责构建模型、Prompt、输出解析器和 Runnable Chain。
- **LangServe**：负责将 Runnable 或 Chain 暴露为 REST API。
- **FastAPI**：负责处理 HTTP 请求并生成 OpenAPI 文档。
- **Pydantic**：负责验证请求数据和描述输入输出 Schema。

整体关系如下：

```text
LangChain Runnable / Chain
          ↓
       LangServe
          ↓
       FastAPI
          ↓
       REST API
```

### 2.2 Runnable、Chain 与 API 的关系

Runnable 是 LangChain 中可以被调用的对象，聊天模型、Prompt、输出解析器以及通过 `|` 组合出来的链都可以作为 Runnable 使用。

Chain 是多个 Runnable 按顺序或结构组合后的执行流程。例如：

```text
Prompt → ChatModel → OutputParser
```

LangServe 不需要了解 Chain 的内部实现，只需要接收一个 Runnable，并为它提供统一的 HTTP 调用入口。

### 2.3 LangServe 的整体工作流程

```text
客户端请求
    ↓
FastAPI 接收请求
    ↓
Pydantic 校验输入
    ↓
LangServe 调用 Runnable
    ↓
LangChain 执行模型或 Chain
    ↓
返回 JSON 或流式响应
```

### 2.4 LangServe 的请求处理流程

1. 客户端向服务端发送请求。
2. FastAPI 根据路由匹配请求。
3. Pydantic 根据 Runnable 的输入 Schema 校验数据。
4. LangServe 将输入传递给 Runnable。
5. Runnable 调用模型或执行 Chain。
6. LangServe 将结果序列化为 JSON 或流式响应。

### 2.5 Pydantic 在请求校验中的作用

Pydantic 根据 Runnable 的输入输出定义生成数据模型，用于：

- 校验请求字段和数据类型。
- 解析 JSON 请求体。
- 描述输入和输出 Schema。
- 为 Swagger / OpenAPI 提供接口信息。

### 2.6 REST API、Schema 与 Swagger 的关系

LangServe 根据 Runnable 自动生成 REST API 和 Schema：

```text
Runnable
   ├── 调用接口：/invoke、/batch、/stream
   ├── Schema 接口：/input_schema、/output_schema
   └── 文档页面：/docs、/openapi.json
```

## 3. API 学习

本章介绍 LangServe 的服务端 API、客户端 API 和自动生成的 HTTP API，完整代码放在第 4 章。

### 3.1 服务端 API

#### 3.1.1 `add_routes()`

`add_routes()` 是 LangServe 最常用的高级 API，用于将 Runnable 注册到 FastAPI 应用：

```python
add_routes(app, runnable, path="/my_runnable")
```

参数含义：

- `app`：FastAPI 应用对象。
- `runnable`：需要发布的模型或 Chain。
- `path`：API 基础路径。

#### 3.1.2 `APIHandler`

`APIHandler` 是更底层的服务端 API，适合需要自己控制 FastAPI 路由、鉴权、请求处理或响应格式的场景。

两者区别：

| API | 特点 | 适用场景 |
| --- | --- | --- |
| `add_routes()` | 自动生成完整接口 | 普通 LangServe 服务 |
| `APIHandler` | 手动控制路由和处理流程 | 高度定制化服务 |

#### 3.1.3 服务端 API 的选择

通常优先使用 `add_routes()`。只有在需要自定义路由、权限校验、请求处理或响应格式时，才使用 `APIHandler`。

### 3.2 客户端 API

#### 3.2.1 `RemoteRunnable`

`RemoteRunnable` 由 LangServe 提供，用于将远程 LangServe API 封装成本地 Runnable：

```python
from langserve import RemoteRunnable

runnable = RemoteRunnable("http://localhost:8000/openai/")
```

它通过 HTTP 调用服务端，但调用方式与本地 Runnable 类似。

#### 3.2.2 `invoke()`

执行一次调用并等待完整结果：

```python
runnable.invoke(input_data)
```

#### 3.2.3 `batch()`

一次提交多个输入：

```python
runnable.batch([input_a, input_b])
```

#### 3.2.4 `stream()`

逐步接收模型或 Chain 的输出：

```python
runnable.stream(input_data)
```

### 3.3 自动生成的 REST API

假设基础路径为 `/my_runnable`，LangServe 通常会生成以下接口：

#### 3.3.1 `/invoke`

```text
POST /my_runnable/invoke
```

对单个输入执行 Runnable。

#### 3.3.2 `/batch`

```text
POST /my_runnable/batch
```

对一批输入执行 Runnable。

#### 3.3.3 `/stream`

```text
POST /my_runnable/stream
```

以流式方式返回输出。

#### 3.3.4 `/stream_log`

```text
POST /my_runnable/stream_log
```

流式返回输出以及部分中间步骤。

#### 3.3.5 `/astream_events`

```text
POST /my_runnable/astream_events
```

流式返回 Runnable 执行过程中产生的事件。

### 3.4 Schema API

#### 3.4.1 `/input_schema`

```text
GET /my_runnable/input_schema
```

查看 Runnable 的输入 Schema。

#### 3.4.2 `/output_schema`

```text
GET /my_runnable/output_schema
```

查看 Runnable 的输出 Schema。

#### 3.4.3 `/config_schema`

```text
GET /my_runnable/config_schema
```

查看 Runnable 支持的配置 Schema。

### 3.5 配置与文档 API

#### 3.5.1 `/c/{config_hash}`

带有 `/c/{config_hash}` 的接口用于调用某个配置版本的 Runnable，例如：

```text
POST /my_runnable/c/{config_hash}/invoke
```

`config_hash` 不是普通编号，不能随意填写 `123`。如果没有由 Playground 或配置分享功能生成有效哈希，应使用不带 `/c/{config_hash}` 的普通接口。

#### 3.5.2 `/docs`

```text
GET /docs
```

查看 Swagger UI 页面，可以查看接口定义并直接测试请求。

#### 3.5.3 `/openapi.json`

```text
GET /openapi.json
```

获取 FastAPI 生成的 OpenAPI JSON 文档。

## 4. 示例

### 4.1 项目运行

#### 4.1.1 使用 `uv` 同步依赖

在项目根目录执行：

```bash
cd /Users/zm/lm/lm-ai-future
uv sync
```

当前项目使用根目录的 `pyproject.toml`、`uv.lock` 和 `.venv`，不再使用子项目独立的 Poetry 配置。

#### 4.1.2 配置 DeepSeek 环境变量

```bash
export DEEPSEEK_API_KEY="你的 DeepSeek API Key"
export DEEPSEEK_BASE_URL="https://api.deepseek.com/v1"
```

也可以在项目根目录的 `.env` 文件中配置，但不要将真实 API Key 提交到 Git 仓库。

#### 4.1.3 启动 LangServe 服务

```bash
uv run python study/day5-langchain-chat-model/02-langserve/app/server.py
```

服务默认监听 `localhost:8000`。

#### 4.1.4 访问 Swagger 页面

打开：

```text
http://localhost:8000/docs
```

也可以查看 OpenAPI JSON：

```bash
curl http://localhost:8000/openapi.json
```

#### 4.1.5 调用普通模型接口

当前 `/openai` 是直接调用聊天模型，输入可以是字符串：

```bash
curl -X POST \
  "http://localhost:8000/openai/invoke" \
  -H "Content-Type: application/json" \
  -d '{
    "input": "你好"
  }'
```

### 4.2 服务端示例

#### 4.2.1 配置 DeepSeek 聊天模型

```python
import os

from langchain_openai import ChatOpenAI

import core.config

llm = ChatOpenAI(
    model="deepseek-chat",
    base_url=os.getenv("DEEPSEEK_BASE_URL"),
    api_key=os.getenv("DEEPSEEK_API_KEY"),
)
```

虽然类名是 `ChatOpenAI`，但通过 `base_url` 可以调用兼容 OpenAI API 格式的 DeepSeek 服务。

#### 4.2.2 使用 `add_routes()` 发布模型

```python
from fastapi import FastAPI
from langserve import add_routes

app = FastAPI(title="LangChain 服务器")

add_routes(
    app,
    llm,
    path="/openai",
)
```

#### 4.2.3 使用 `StrOutputParser` 发布 Chain

```python
from langchain_core.output_parsers import StrOutputParser

parser = StrOutputParser()

add_routes(
    app,
    llm | parser,
    path="/openai_str_parser",
)
```

#### 4.2.4 使用 Prompt 和模型发布 Chain

```python
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_template("告诉我一个关于 {topic} 的笑话")

add_routes(
    app,
    prompt | llm,
    path="/openai_ext",
)
```

调用时需要传入 `topic`：

```json
{
  "input": {
    "topic": "猫"
  }
}
```

#### 4.2.5 使用 `APIHandler` 自定义路由

当 `add_routes()` 的自动接口不能满足需求时，可以使用 `APIHandler`，自行定义 FastAPI 路由、认证和请求处理流程。

该方式适合高级场景，当前项目的普通服务仍使用 `add_routes()`。

#### 4.2.6 配置 CORS

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
    expose_headers=["*"],
)
```

生产环境不建议长期使用 `allow_origins=["*"]`，应根据实际前端域名限制允许来源。

#### 4.2.7 当前项目服务端路由

当前服务注册了三个 Runnable：

- `/openai`：直接调用模型。
- `/openai_str_parser`：调用模型并解析字符串输出。
- `/openai_ext`：先使用 Prompt，再调用模型。

完整代码位于：

```text
study/day5-langchain-chat-model/02-langserve/app/server.py
```

### 4.3 客户端调用示例

#### 4.3.1 使用 `RemoteRunnable`

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableMap
from langserve import RemoteRunnable

openai = RemoteRunnable("http://localhost:8000/openai/")
prompt = ChatPromptTemplate.from_messages(
    [
        ("system", "你是一个喜欢写故事的助手"),
        ("user", "写一个故事，主题是：{topic}"),
    ]
)

chain = prompt | RunnableMap({"openai": openai})
```

#### 4.3.2 使用 `invoke()`

```python
response = chain.invoke({"topic": "猫"})
print(response)
```

#### 4.3.3 使用 `batch()`

```python
response = chain.batch([
    {"topic": "猫"},
    {"topic": "狗"},
])
print(response)
```

#### 4.3.4 使用 `stream()`

```python
for chunk in chain.stream({"topic": "猫"}):
    print(chunk, end="", flush=True)
```

#### 4.3.5 使用 Python `requests`

```python
import requests

response = requests.post(
    "http://localhost:8000/openai_ext/invoke",
    json={"input": {"topic": "猫"}},
)

print(response.json())
```

#### 4.3.6 使用 `curl`

```bash
curl -X POST \
  "http://localhost:8000/openai_ext/stream" \
  -H "Content-Type: application/json" \
  -d '{
    "input": {
      "topic": "狗"
    }
  }'
```

#### 4.3.7 使用 TypeScript 客户端

```typescript
import { RemoteRunnable } from "@langchain/core/runnables/remote";

const chain = new RemoteRunnable({
  url: "http://localhost:8000/openai/",
});

const result = await chain.invoke("你好");
console.log(result);
```

### 4.4 Docker 部署示例

#### 4.4.1 Dockerfile 的作用

Dockerfile 用于描述如何构建包含 Python、项目依赖和 LangServe 应用的镜像，并在容器启动时运行 Uvicorn。

当前项目统一使用 `uv`，Docker 构建时应以根目录的 `pyproject.toml` 和 `uv.lock` 为准。

#### 4.4.2 构建 Docker 镜像

在项目根目录执行：

```bash
docker build -t lm-langserve .
```

#### 4.4.3 启动 Docker 容器

```bash
docker run --rm \
  -p 8000:8000 \
  -e DEEPSEEK_API_KEY="$DEEPSEEK_API_KEY" \
  -e DEEPSEEK_BASE_URL="$DEEPSEEK_BASE_URL" \
  lm-langserve
```

#### 4.4.4 配置端口和环境变量

容器内部服务监听 `8000` 端口时，可以通过 `-p 8000:8000` 映射到宿主机。API Key 应通过环境变量或安全的密钥管理服务注入，不要写入镜像或提交到代码仓库。

## 5. 常见问题

### 5.1 根路径返回 404

LangServe 默认主要提供注册 Runnable 产生的 API，不会自动为 `/` 定义页面。访问 `/docs` 查看 Swagger 文档。

### 5.2 API Key 未配置

确认 `DEEPSEEK_API_KEY` 已配置，并且启动服务的终端能够读取该环境变量或项目根目录的 `.env` 文件。

### 5.3 DeepSeek `base_url` 配置错误

确认 `DEEPSEEK_BASE_URL` 与项目其他 DeepSeek 示例使用的配置一致，并确保 `ChatOpenAI` 同时接收 `base_url` 和 `api_key`。

### 5.4 LangChain 版本导致的导入错误

当前项目使用 LangChain 1.x 风格的导入路径：

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableMap
```

旧教程中的 `langchain.prompts` 或 `langchain.schema.runnable` 可能无法在当前依赖环境中导入。

### 5.5 请求体格式错误

调用 `/openai/invoke` 时，输入通常是字符串；调用 `/openai_ext/invoke` 时，输入需要包含 `topic`：

```json
{
  "input": {
    "topic": "猫"
  }
}
```

具体格式以对应 Runnable 的 `/input_schema` 为准。

### 5.6 `config_hash` 缺失或无效

`/c/{config_hash}/invoke` 中的 `config_hash` 不是普通编号，不能随意填写 `123`。

如果没有由 Playground 或配置分享功能生成有效的配置哈希，应使用普通接口：

```text
/openai/invoke
/openai_ext/invoke
```

### 5.7 Swagger 调用接口失败

在 Swagger 页面中要选择正确的接口：

- 直接模型：`POST /openai/invoke`
- Prompt Chain：`POST /openai_ext/invoke`
- 不要直接使用：`POST /openai/c/{config_hash}/invoke`

如果接口仍然失败，应依次检查服务是否启动、环境变量是否配置、请求体是否符合 Schema，以及模型服务是否可访问。
